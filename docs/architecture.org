* The boundaries are the design

- *No SCM escapes the bridge.*  =src/guile_bridge.h= has no Scheme type in any
  signature, and nothing outside =guile_bridge.c= calls =scm_*=.  The rest of
  the shell builds and is tested from plain structs, and the built-in fallback
  bar is built the same way, with no Scheme at all.
- *A module is a value, not a subclass.*  A kind, a root widget, an =update=
  function, a =destroy= function, and the factory table in =module.c=.  Adding
  one is three steps: a =.c= file with a factory, its prototype in
  =src/modules/modules.h=, and a row in the table.  Nothing else changes.
- *A bar is a surface, and a surface is not a bar.*  =src/surface.c= owns the
  layer-shell plumbing (edge, anchors, margins, exclusive zone, monitor,
  namespace).  A notification stack is the same object with a different child;
  that is why the next surface does not have to re-learn layer-shell.
- *CSS is structure plus skin.*  =resources/css/whelk.css= is the structure:
  module layout, hover, workspace states, the battery's warning colours.  The
  skin -- this bar's colours, fonts and radius -- is generated from the
  configuration and scoped to the bar's window id, so two bars can wear two
  materials.

* How a bar becomes pixels

#+name: bar-pipeline
#+caption: A bar crosses four layers, and each one can be tested without the next.  A reload throws the last three away and builds them again.
#+begin_src mermaid
flowchart LR
    A["(bar #:name 'main ...)<br/>a Scheme record"] --> B["an alist<br/>state.scm: bar->alist"]
    B --> C["WhelkBarConfig<br/>plain C structs, deep-copied"]
    C --> D["WhelkBar<br/>bar.c"]
    D --> E["WhelkSurface<br/>edge, anchors, margin,<br/>exclusive zone, monitor"]
    D --> F["module rows<br/>left, centre, right, overflow"]
    F --> G["WhelkModule<br/>a root widget + a timer"]
    D --> H["a generated CSS provider<br/>scoped to this bar's window"]
    I["resources/css/whelk.css<br/>the structure"] --> H
    H --> J["the bar on screen"]
    E --> J
    G --> J
#+end_src

The deep copy is what makes a reload safe: the C structs do not point into the
Scheme heap, so destroying every bar and building new ones from a fresh
evaluation has nothing to reconcile.  A module's own generation guard covers the
other direction -- a command that finishes after its module was freed writes
nowhere (see [[file:lifecycle.org][Lifecycles]]).

* Where a change belongs

| You are adding                        | It goes in                                          |
|---------------------------------------+-----------------------------------------------------|
| a reading on the bar                  | =src/modules/<kind>.c=, =modules.h=, a row in =module.c= |
| an option every module understands    | the shared reader in =src/config.c= and the table in =guile_bridge.c= |
| a bar or widget keyword               | =guile_bridge.c= (read), =config.h= (carry), =bar.c= (use) |
| a new kind of surface                 | =src/surface.c= as the parent, then its own file       |
| a palette                             | =scheme/whelk/themes.scm=                             |
| a menu producer                       | =src/modules/menu.c=, in the probing order            |
| a settings-window control             | =src/preferences.c= and the page it belongs to        |
| a new configuration entry point       | =scheme/whelk/core.scm=, and it must still be a value |
