#+title: The lock screen
#+subtitle: whelk documentation
#+options: toc:nil num:nil

How whelk reaches the separate hasp lock screen, and what happens when it is not
installed.

#+begin_quote
The lock screen, its surfaces, PAM conversation, retry policy, logind watcher
and Scheme theme are the separate [[https://github.com/jjba23/hasp][hasp]] project.
Whelk owns only the request and the idle timer that reaches it.  There is no
lock-screen code, PAM linkage or PAM build dependency in this repository.
#+end_quote

* The runtime contract

Whelk never links hasp.  It starts the program, so the two projects can be
built, packaged, upgraded and tested independently.

| Whelk action       | Program                    | When |
|--------------------+----------------------------+------|
| a lock request     | =hasp --lock=               | =--lock=, the shell menu, logind triggers and the idle timer |
| logind following   | =hasp --watch=              | once, when the shell starts |
| =--check-lock=     | =hasp --check=              | the diagnostic command, then exit |

The lock itself is a separate =hasp --lock-now= process.  Whelk does not keep a
lock surface in its own process, so a shell exit cannot take an active lock
screen with it.

* Finding hasp

The program is chosen in this order:

1. =HASP_BIN=, when set;
2. a sibling =hasp= beside the running =whelk= binary;
3. =hasp= on =$PATH=.

A packaged whelk should recommend or depend on hasp rather than build it in.
The Nix expression takes an optional =hasp= argument and adds it to the
wrapper's =PATH= when supplied; the Guix and distribution packages leave it as
a runtime recommendation.

Without hasp the shell still starts and every non-lock feature works.  A lock
action prints:

#+begin_src text
whelk: hasp could not be started: No such file or directory (os error 2); install hasp or set HASP_BIN
#+end_src

and =--check-lock= exits with the same explanation.  This is a missing optional
program, not a broken shell.

* Configuration

Hasp owns its own configuration:

- =$XDG_CONFIG_HOME/hasp/theme.scm= (or =~/.config/hasp/theme.scm=) is its
  Scheme theme;
- =HASP_SCHEME_DIR= points a development or staged install at the module tree;
- =HASP_LOCK_STRICT=, =HASP_LOCK_STATE_FILE= and the other =HASP_*= variables
  are documented in hasp's README.

Whelk does not read, rewrite or validate those files.

* Logind and the parent-death signal

Whelk starts one =hasp --watch= process at shell startup.  The watcher follows
logind's =Lock=, =PrepareForSleep(true)= and session =Active=false= signals.
Whelk asks Linux to terminate that watcher when the shell exits, so a restart
does not leave a second watcher behind.  A lock screen already started by the
watcher is a separate process and is deliberately not tied to the shell's
lifetime.

If logind has no session for the process, hasp reports that once and keeps
running; a lock can still be requested explicitly.

* Where the policy lives

The fail-closed presentation policy, the PAM service choice, the retry delay,
the password handling and the lock screen's own diagnostics are hasp's.
[[https://github.com/jjba23/hasp][That project's README and `--check` output]] are the
reference; whelk's =--check-lock= is only a pass-through.
