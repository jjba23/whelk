#+title: Menus
#+subtitle: whelk documentation
#+options: toc:nil num:nil

A menu bar's left half: the shell's own menu and the focused application's File/Edit/View, from six producers.

* The shell menu and the global menu
:PROPERTIES:
:CUSTOM_ID: menus
:END:

The left half is a menu bar's: the machine's own menu behind a mark (the whelk,
where the apple is), then that application's =File=, =Edit= and =View=.  The
built-in bar is =(list (start-module) (menu-module #:app-name? #f))=; both are
modules, so a bar that wants another order, or the window's name between them,
writes another list -- =(window-module ...)= is still there for that.

** The shell menu
:PROPERTIES:
:CUSTOM_ID: shell-menu
:END:

=start-module= is the machine's own menu, and it is configuration rather than a
compiled table: `(whelk menu)' units written with the settings file, or
=default-shell-menu= when the file writes none.  The default is the Apple menu's
shape in this desktop's words -- =About This System=, =Control Panel=,
=Software…=, a =Recent Items= submenu, =Force Quit…=, =Sleep=, =Restart…=,
=Shut Down…=, =Lock Screen= and =Log Out= -- followed, after a rule, by the
launcher, a reload and the way out.  The panels are deliberately absent: they
are bar modules with their own clicks, and =whelk --network wifi=,
=--network bluetooth= and =--notifications= are their command-line homes.  What
the menu does is what its entries say: =About= is a real
GTK about dialogue naming the machine, the session and the toolkit;
=Control Panel= opens whelk's own GUI settings window for the loaded
configuration;
=Recent Items= is GTK's recent-documents list, filled when the submenu opens;
=Force Quit…= opens the launcher in its =quit= mode, where the open windows are
listed and Enter closes the chosen one.

An action is one of two things, and the spelling is the difference: a string
beginning with =shell:= is something the shell does itself (=about=, =settings=,
=launcher=, =force-quit=, =network=, =bluetooth=, =notifications=, =dnd=,
=lock=, =reload=), and anything else is a command line.  A submenu given a string
instead of children is a slot the shell fills when it opens.

#+begin_src scheme
  (configure-shell!
   #:shell-menu
   (list (menu-item "About This System" "shell:about")
         (menu-item "Control Panel" "shell:settings")
         (menu-separator)
         (menu-submenu "Recent Items" "shell:recent-items")
         (menu-separator)
         (menu-item "Force Quit…" "shell:force-quit")
         (menu-separator)
         (menu-item "Sleep"
                    "loginctl suspend 2>/dev/null || systemctl suspend 2>/dev/null || zzz")
         (menu-item "Lock Screen" "shell:lock")
         (menu-item "Search…" "shell:launcher"))
   #:bars (list (default-bar)))
#+end_src

The default menu's ways out are chains rather than =systemctl= verbs, so the
same menu sleeps and shuts down on a systemd machine, an elogind one and a
machine with neither; [[file:portability.org][Portability]] lists the chains.

The mark is one ribbon spiralling from a thin spire out to a wide lip, drawn
from a formula in the bar's own ink at =#:icon-size= pixels (18 by default), so
no icon file or icon theme is needed for it; a configuration that wants a
glyph instead sets =#:label=.  The menu walks with the keyboard -- Down and Up
through the rows, Right into a submenu, Escape out -- which is the least a menu
that replaces a menu bar has to do.

** The application's menus
:PROPERTIES:
:CUSTOM_ID: app-menus
:END:

=menu-module= puts the focused application's menus on the bar.  These producers
supply them, in that order:

#+name: menu-producers
#+caption: What the menu bar asks, and in which order.  The first answer wins; a configuration's own menu wins over every protocol.
#+begin_src mermaid
flowchart TD
    F["focus changes"] --> C{"#:menu-command set?"}
    C -->|yes| CMD["run the command<br/>Menu TAB Item TAB Chord TAB Command"]
    CMD --> DONE["the menubar is the answer"]
    C -->|no| BASE["build the fallback from the<br/>dictionary, the Orbit corpus,<br/>and the shared Edit and View"]
    BASE --> P{"does the application<br/>publish a menubar?"}
    P -->|"org.gtk.Menus"| GTK["read Start, follow Changed"]
    P -->|"com.canonical.dbusmenu"| DBUS["GetLayout, follow LayoutUpdated<br/>click = Event(id, clicked)"]
    P -->|"AT-SPI menu bar"| ATSPI["walk the accessibility tree<br/>click = DoAction"]
    P -->|no| BASE
    GTK --> DONE
    DBUS --> DONE
    ATSPI --> DONE
#+end_src

- *A menu the configuration names.*  =#:menu-command= runs a program that prints
  =Menu<TAB>Item<TAB>Chord<TAB>Command= lines (with =-= for a rule and
  =File>Export= for a submenu), and its answer becomes the application's
  menubar.  That is the escape hatch for an application no bus describes, and it
  needs no rebuild: the command is read on every focus change.
- *The application's own menubar, over D-Bus.*  GTK's
  =gtk_application_set_menubar()= publishes it through =org.gtk.Menus= on the
  application's bus name, so the labels, the actions, the checkmarks and the
  greyed-out items are the application's own.  On X11, GTK also exports the
  exact bus name and menu object paths as =_GTK_*= properties on the focused
  window; whelk reads =_GTK_UNIQUE_BUS_NAME=,
  =_GTK_APPLICATION_OBJECT_PATH=, =_GTK_MENUBAR_OBJECT_PATH= and the
  window/app-menu paths, and tries them before the conventional paths under
  the application id -- application-wide and window-scoped -- and GTK's
  anonymous application.  The menu is *followed*: =org.gtk.Menus= has a
  =Changed= signal, so whelk subscribes before it calls =Start= and asks
  =Start= again for the current tree instead of keeping the one it drew.  That
  makes Firefox, LibreOffice and other X11 GTK applications work even when
  their =WM_CLASS= is not a valid bus name, and a menu that grows while it is
  open stays true -- without closing, as *A menu that stays open* explains below.
- *The application's own menu, as DBusMenu.*  Qt, KDE and everything that
  registers with =com.canonical.AppMenu.Registrar= publishes =com.canonical.dbusmenu=
  instead: a tree of (id, properties, children).  whelk reads =GetLayout= and
  keeps each entry's id, so choosing one sends =Event(id, "clicked")= back to
  the application -- the application's own menu, carried out by the
  application itself.  Its =shortcut= property is shown beside the label in
  the style the bar asked for, and the menu is *followed* rather than
  remembered: =LayoutUpdated= and =ItemsPropertiesUpdated= make the shell read
  the layout again, ids included, and the tree that comes back replaces the
  one on screen before a click can use a stale id.
- *On X11, the registrar fills in the exact DBusMenu path.*  Exact
  =org.gtk.Menus= paths are still tried first; after them,
  =com.canonical.AppMenu.Registrar= maps the focused window's id to the exact
  bus and object path an application chose, so a Qt or KDE menu no longer has
  to live at =/MenuBar/1=.  Its answer is tried before the conventional
  DBusMenu paths; the registrar is optional, and its absence costs one failed
  call and never the bar.
- *The accessibility tree, as a last protocol.*  AT-SPI is not a menu protocol,
  but GTK, Qt and Electron already publish their menus there as accessible
  objects: a =MENU_BAR= whose children are =MENU= objects and =MENU_ITEM=s with
  names, states, key bindings and an =Action= interface.  Reading those labels
  is the one producer that gives an application's own translated menu when it
  publishes neither =org.gtk.Menus= nor DBusMenu.  The tree is walked on a
  worker thread, after both D-Bus protocols have found nothing, and that walk
  is followed: the registry is told which object events matter and
  =ChildrenChanged=, =PropertyChange=, =StateChanged= and
  =VisibleDataChanged= for the focused application re-read and replace the
  tree, just as =org.gtk.Menus'= =Changed= does.  Choosing an entry sends
  =DoAction= to its accessible object.  A program that only builds its menu
  after the native menu was opened once has no passive tree to read, and falls
  back to the dictionary like before.
- *The dictionary.*  Most applications publish nothing, so their menus are
  written from their documented shortcuts: one hundred and thirteen
  applications answering to three hundred and fifteen ids -- the browsers,
  terminals, editors (Emacs among them, with its multi-key chords stored as
  sequences), file managers, office suites, mail clients, graphics tools, media
  players, PDF readers, chat clients, video editors, DAWs, note-taking
  applications, developer tools, archive managers, system panels, GNOME's own
  small programs, a few games and the CAD and 3D applications a desktop
  actually has -- each with the menus it really has.
  Every entry shows its chord on the right and types it into the focused
  window when it is chosen (=wtype= on Wayland, =xdotool= on X11).  An
  application the dictionary does not know is not given a File menu it might
  not have.
- *The Orbit Global Menu corpus, built in as Scheme.*
  [[https://github.com/Unmade760/orbit-global-menu][Orbit]] maintains a
  reviewed table of 293 applications, with nested submenus, menu separators,
  9,800 shortcuts and 1,702 deliberately greyed placeholders.  That corpus is
  now =scheme/whelk/orbit.scm=, generated from Orbit's JSON and read by the
  same Guile bridge as the dictionary, so the common case needs no download.
  The data keeps its own GPL-3.0-or-later header; the Guile bridge and the rest
  of whelk stay MIT.  The curated dictionary still wins for an application it
  knows; Orbit fills the gap.  A user-installed JSON map under
  =WHELK_SHORTCUT_MAPS=, =$XDG_CONFIG_HOME/global-menu/shortcuts/apps= or
  =$XDG_DATA_HOME/global-menu/shortcuts/apps= still overrides the built-in
  corpus, which is how a local correction is tested without a rebuild.  An
  item without a shortcut is greyed rather than invented; an integer =target=
  is not representable in whelk's menu model, so that small set stays greyed
  too.
- *The shared Edit and View.*  For everything else, the shortcuts every
  application shares, in the same shape and with the same chords on the right,
  plus the synthesized File and Window actions: desktop actions, a new window,
  closing the focused window, and the compositor's arranging verbs.  When an
  Orbit or dictionary menu replaces the application's own menus, those
  synthesized menus with labels the application did not supply -- notably
  =Window= -- stay beside it.

Every producer shows the key its entries answer to.  A D-Bus menubar may
publish an =accel= attribute for an item, and it is read and printed beside
the label; the dictionary's entries print the chord they type.  What a chord
is stored as and what is printed are separate: the dictionary may write one in
Emacs notation (=C-v=, =M-F4=, =C-S-p=) or in CUA notation (=Ctrl+V=,
=Alt+F4=), and the runtime translates either into the keys the focused window
receives.  =#:accelerator-style= chooses what the menu prints -- ='cua= by
default, ='emacs= for the notation an Emacs user reads -- and the same entry
types the same keys either way.

A chord may be a sequence: =C-x C-s= is two chords, held and typed in order,
and it is stored and printed as the Emacs user writes it.  =wtype= and
=xdotool= receive one command per chord, so the prefix is not lost between
them.

The name of the application in front can come first -- a menu button named
after the application, holding what belongs to the application rather than to a
document or a window:

- the =About=, =Preferences= / =Settings= (or =Options=) and =Help= rows the
  application publishes itself, lifted from its own menus with their own
  actions and accelerators, at any depth (Preferences is usually one level
down, under Edit);
- the extra ways its desktop entry says it can be started -- =New Window= and
  the entry's declared =Actions=, built from its =Exec= lines;
- =Quit <Application>=, the session's close command.

The window verbs (maximize/restore, toggle floating, move, full screen) stay in
the Window menu and =Close Window= stays in File, so no row appears in two
menus.  An application that publishes no About or Preferences row simply has a
shorter menu; one with no close command on this session has only the rows it
does publish.  On the default bar the application button is off
(=#:app-name? #f=), because the window module beside it already says whose
window you are in, and a menu bar says it once.

The menu bar is usable from the keyboard: Down and Up walk the entries, Home
and End go to the ends, Left and Right move between File, Edit and View, Right
opens a submenu, and Escape closes.  A submenu wears a chevron rather than a
second label.

The shared Edit menu covers the whole editing path, not only the clipboard:
Undo and Redo; Cut, Copy, Paste, Paste and Match Style and Select All; Find,
Find Next (F3), Find Previous (Shift+F3) and Replace.  The shared View menu
adds Reload (Ctrl+R) to the zoom and full-screen entries.  The dictionary's
standard Edit list carries the same additions where the application documents
them, so a known editor gets them too.

The shortcut menus need something that can type a chord: with neither =wtype=
nor =xdotool= installed, an application gets no shared Edit and View, rather
than entries that could not work.  Its desktop actions and =New Window= still
fill the application menu, =Close Window= is there in File when the compositor
can close, and the =Window= menu still carries its arranging verbs, so a sparse
menu is useful even without a typing tool.  An application that publishes its own menubar keeps the
application's own Window menu instead.

The dictionary is not a placeholder.  A Wayland shell learns a GTK
application's menu paths from the compositor's =gtk-shell= protocol, which niri
does not implement, so on niri most applications will be served by it or by
the built-in Orbit corpus.  The dictionary is Scheme, in
=scheme/whelk/menudict.scm=:
adding an application is one form -- its name, the ids it answers to, then its
menus -- and nothing else.  The shell reads the table at startup and after every
reload, so a settings change does not need a rebuild.

=add-menu-app= appends an application the table does not know, and
=replace-menu-app= puts yours in the place of the entry that answers to an id --
the entry claiming that id is dropped, so a wrong chord or a whole wrong menu is
corrected without giving up the rest of the table.  Both are available in a
settings file and at the REPL:

#+begin_src scheme
  ;; An application the table does not know: name, ids, menus.  Chords may be
  ;; written the Emacs way: C-, M- and S- are Ctrl, Alt and Shift.
  (add-menu-app "Steam" '("steam" "com.valvesoftware.Steam")
                '(("File" ("Settings" "C-,"))
                  ("View" ("Full Screen" "F11"))))

  ;; The built-in Firefox, with the menus you want instead.
  (replace-menu-app "firefox" "Firefox"
                    '("firefox" "org.mozilla.firefox")
                    '(("File" ("Open" "C-o"))
                      ("Edit" ("Undo" "C-z"))))
#+end_src

An item is =(label chord)=: the chord is written in Emacs notation or in CUA
notation, and the runtime translates it into the modifiers to hold and the key
to press.  It may also be a sequence: =(label "C-x C-s")= is two chords, typed
in order.  The long form =(label chord modifiers key)= is still read for a key
the parser cannot spell, with =modifiers= =#f= when the key is typed alone.
Neither form trusts its argument: an entry whose item has no chord, whose menu
is empty, or whose two items type the same chord is refused and logged with the
reason -- =[WARN][whelk][Scheme:Menus] Broken is not a menu application: an
item needs a label and a chord, or the long label/chord/modifiers/key form= --
because a dictionary that silently drops what you wrote is worse than one that
says why.  Replacing an id the table does not answer to is reported too, and
added rather than lost.  A reload starts from the built-in table again, so
saving the file replaces your edits instead of stacking another copy of them in
front.

** A menu that stays open
:PROPERTIES:
:CUSTOM_ID: menu-stays-open
:END:

An application re-publishes its menus constantly, and not because anything a
reader can see changed: =AboutToShow= asks for a fresh layout the moment a menu
opens, a hover sends =ItemsPropertiesUpdated= (a checkmark, an entry that
became enabled), a bookmarks or recent-documents menu is built when it is asked
for.  A menu bar that rebuilt on every one of those takes the menu away from
the person reading it, which is why the global menu used to close itself a
moment after it opened.

So a tree is compared before it is adopted: if the menus, the rows, the labels,
the chords, the enabled state and the ids a click would send are the same,
nothing happens at all.  If they really changed, the tree is rebuilt and the
menu that was open is put back on the new rows, in the same place: the
top-level menu by its label, every open submenu by its label, and the keyboard
focus on the row it was on.  A label that no longer exists stops the descent at
the deepest level that does exist, and the menu stays open there rather than
disappearing.

#+name: menu-republish
#+caption: What a re-published tree does to the menu on screen.
#+begin_src mermaid
flowchart TD
    A["the application re-publishes its menu<br/>Changed, LayoutUpdated, a hover"] --> B{"same menus, rows, chords,<br/>enabled state and ids?"}
    B -->|yes| C["nothing is rebuilt<br/>the menu stays exactly as it is"]
    B -->|no| D["the open menu is remembered by label<br/>top-level, submenus, focused row"]
    D --> E["the new tree is rendered"]
    E --> F{"does the same top-level<br/>label still exist?"}
    F -->|no| G["the menu closes:<br/>what was being read is gone"]
    F -->|yes| H["the same menu opens again,<br/>each submenu down the path,<br/>focus on the row it was on"]
    H --> I{"a submenu label vanished?"}
    I -->|yes| J["stay open at the deepest<br/>level that still exists"]
    I -->|no| K["the menu is where it was"]
#+end_src

The ids are what makes the rebuild safe: the DBusMenu read that answers
=LayoutUpdated= carries the new ids before the new rows are shown, so a click
never sends =Event()= with an id from a layout that is gone.

What this does not change: choosing a row closes the menu, a click outside
closes it, and a focus change to another application closes it and builds that
application's menus.

** The shell menu
:PROPERTIES:
:CUSTOM_ID: menu-rust
:END:

whelk has its own =menu= module.  It is the same menubar in the same
place, built from owned Rust data rather than widgets assembled by hand:
=rust/src/menubar.rs= reads the script protocol, =org.gtk.Menus= and DBusMenu;
=rust/src/menuapps.rs= owns the application dictionary, Orbit corpus and
=desktop-entry= fallbacks; =rust/src/atspi.rs= reads the accessibility tree; and
=rust/src/globalmenu.rs= owns the focused-window poll, the producer chain, the
popovers and keyboard navigation.  =#:menu-command=, =#:shortcuts?=,
=#:app-name?=, =#:accelerator-style= and =#:shortcut-tool= keep their meanings.

The producer order is deliberate:

1. =#:menu-command=;
2. =org.gtk.Menus=, exact X11 paths first then the conventional ones --
   =menubar=, =AppMenu= and the lower-case =appmenu= that
   =GtkApplication::set_app_menu= publishes;
3. =com.canonical.dbusmenu=, after the X11 registrar has supplied the exact
   bus and object path;
4. AT-SPI, read on a worker thread and followed live through
   =org.a11y.atspi.Event.Object=;
5. the curated application dictionary, then the shipped Orbit corpus, then the
   shared Edit/View and compositor Window rows.

A dictionary or Orbit row types its documented chord into the focused window;
AT-SPI rows use =DoAction= on the accessibility bus.  Desktop entries supply
New Window and the entry's named actions from their =Exec= lines to the
application menu, and Close Window in File.  A menu a producer sends with an
empty label gets no button: it is a placeholder, not a menu.

Current boundaries are narrow, and stated rather than hidden:

- =org.gtk.Menus.Changed= and DBusMenu =LayoutUpdated=/=ItemsPropertiesUpdated=
  are followed live through =rust/src/menuwatch.rs=: a burst costs one debounced
  re-read (120 ms), a change during a read owes exactly one more, and a tree
  that says the same thing as the one on screen is not rebuilt.  A tree that
  really changed is rebuilt and closes the open menu; =LayoutUpdated= on its
  own closes nothing.
- User-installed Orbit JSON maps under =global-menu/shortcuts/apps= or
  =WHELK_SHORTCUT_MAPS= are read by the Rust producer, which indexes the
  sorted files with the configuration, reads the matching file lazily, and
  places the map before the shipped Scheme corpus and after the curated
  dictionary.
- A malformed or cyclic D-Bus or accessibility tree is truncated or refused
  instead of panicking, and every asynchronous answer is checked against the
  generation of the application in front.

** What the menus do not do yet
:PROPERTIES:
:CUSTOM_ID: menu-limits
:END:

A menu from =#:menu-command= is a snapshot of when the focus moved: the command
is run on a focus change, and nothing tells the shell that its output changed.
On Wayland, both D-Bus protocols still fall back to the conventional object
paths: a compositor that does not expose window properties cannot give whelk an
X11 window id or =_GTK_*= metadata to discover.  On X11 the exact paths and the
registrar are used first.  A window action (=win.*=) is sent to the
application's first window object, and an Orbit action that needs an integer
=target= stays greyed because whelk's action model carries only a string
parameter.
The dictionary covers one hundred and thirteen applications and their
documented shortcuts: it is a curated list, not a guess, and an application
that is not in it gets the shared Edit and View -- unless a settings file adds
it.  The panels, the toasts and the menus open on the compositor's first
monitor; a bar's =#:monitor= is its own.
